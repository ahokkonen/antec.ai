# ADR-0001: LLM-шлюз v1: LiteLLM за адаптером, с закреплёнными версиями

- Статус: принято
- Дата: 2026-11-21
- Ответственный: CTO
- Связанные: ADR-0004, [architecture/overview.md](../architecture/overview.md)
- Уточнено в [ADR-0018](0018-litellm-on-base-layer.md) (версия 1.108.8, секреты без Vault, итоги PoC)

## Контекст

Нужен собственный LLM-шлюз с OpenAI-совместимым API: маршрутизация на OpenRouter, OpenAI,
Anthropic (в v2 ещё локальные модели), виртуальные ключи, бюджеты на пользователя и команду,
учёт расходов. До 500 пользователей на инсталляцию, сервер без GPU, команда DevOps начинающая.

У LiteLLM в 2026 году два инцидента цепочки поставок: в марте вредоносные 1.82.7 и 1.82.8
(через заражённый Trivy GitHub Action в их CI), 21.10.2026 вредоносный 1.107.0 на PyPI и в
Docker-образах, включая плавающие теги `latest`, `main-latest`, `main-stable`. После инцидента
проект сменил ключ подписи, выпустил 1.106.3+ и линию 1.108 (LTS), с 1.110.0 (18.11.2026)
образы подписываются keyless через Sigstore.

Функции LiteLLM Enterprise (платно): SSO для админки свыше 5 пользователей, OIDC/JWT-аутентификация
клиентов, журнал аудита админ-действий, SCIM. В OSS: виртуальные ключи, бюджеты и лимиты,
учёт расходов, админка, балансировка, хуки гардрейлов, MCP-шлюз.

## Варианты

| Вариант | Версия, лицензия | Плюсы | Минусы | Поддержка |
| --- | --- | --- | --- | --- |
| **LiteLLM** | 1.108.x LTS / 1.110.0, MIT + enterprise/ | Больше всего провайдеров, зрелые бюджеты и ключи в OSS, большое сообщество | Два скомпрометированных релиза в 2026; SSO, JWT и аудит платные; хранит все ключи провайдеров | Средняя |
| Bifrost | HTTP 2.3.2, Apache 2.0 | Go, быстрый, ключи и бюджеты в OSS | Расширенный governance в Enterprise, меньше сообщество | Низкая |
| agentgateway | 1.6.0, Apache 2.0, Linux Foundation | LLM + MCP в одном, нейтральный фонд | Молодой как LLM-шлюз, нужен PoC | Низкая |

## Решение

LiteLLM OSS в v1, по требованию CTO, при следующих условиях:

1. **Только версии из `policy/allowed-versions.yaml`.** Сейчас разрешена 1.108.7 (линия LTS),
   кандидат 1.110.0 после карантина. Образ только по digest. Плавающие теги и rc/dev запрещены.
   Перед первым pull: сверка с denylist, проверка подписи cosign, фиксация digest в реестре.
2. **Python-пакет `litellm` не импортируется в наш код.** Используем только HTTP к контейнеру.
   Так компрометация PyPI-пакета не попадает в наши сервисы.
3. **Конечные пользователи не аутентифицируются в LiteLLM.** Platform API ходит служебным ключом
   и передаёт id пользователя для учёта и бюджета. Coding-агенты получают личные виртуальные ключи,
   которые выпускает и отзывает Platform API через management API LiteLLM (OSS).
   Платные JWT и SSO не нужны: в админке LiteLLM не больше 5 администраторов.
4. **Аудит не зависит от LiteLLM.** Конфигурация моделей и маршрутов хранится в git (GitOps),
   выпуск ключей и бюджеты идут через Platform API и попадают в наш аудит. Расходы по каждому
   запросу дублируются в БД Platform API через колбэк или OTel.
5. **Харденинг.** Админка и management API только во внутренней сети; `disable_env_credential_login: true`;
   master key и ключи провайдеров в OpenBao; исходящий трафик LiteLLM разрешён только к API провайдеров;
   отдельная БД и роль в PostgreSQL; MCP-шлюз LiteLLM не используем (ключи провайдеров и токены
   пользователей не собираются в одном процессе).

## Последствия

- Плюс: быстрый старт, широкий выбор провайдеров, бюджеты из коробки.
- Минус: остаётся риск цепочки поставок самого шлюза. Снижаем закреплением по digest, карантином,
  мониторингом advisories и ротацией ключей провайдеров (лимиты расходов у провайдеров обязательны).
- Минус: учёт расходов дублируется (LiteLLM и Platform API). Это осознанно: источник истины наш.
- Сделать: PoC на 1 неделю (бюджет на пользователя по `user`, отчёт расходов, колбэк в Platform API,
  проверка подписи образа), затем зафиксировать digest.

## План выхода

Все клиенты используют OpenAI-совместимый API и логические имена моделей. Управление ключами и
бюджетами идёт через адаптер `GatewayAdmin` (create_key, revoke_key, set_budget, get_spend).
Замена на Bifrost или agentgateway: новый адаптер, перенос конфигурации моделей, перевыпуск
ключей coding-агентов. История расходов остаётся в Platform API. Оценка: 1-2 недели.

## Допущения и открытые вопросы

- Допущение: бюджеты на конечного пользователя через параметр `user` работают в OSS. Проверить в PoC.
- Допущение: 1.108.7 существует и является последним патчем линии LTS на 21.11.2026; сверить с release notes.

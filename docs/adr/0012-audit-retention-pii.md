# ADR-0012: Аудит отдельно от observability, сроки хранения, PII

- Статус: предложено
- Дата: 2026-11-24
- Ответственный: CTO
- Связанные: ADR-0003, ADR-0006, ADR-0008, ADR-0010, ADR-0011, ADR-0013 (в очереди),
  ADR-0015 (в очереди), ADR-0017, ADR-0018, [context/requirements.md](../context/requirements.md)

## Контекст

Сроки хранения противоречат друг другу: ADR-0006 допускал 180 дней для истории, requirements.md
предлагал 12+ месяцев для метаданных аудита и 30-90 дней для содержимого. Удалять данные не может
ни одна роль. Владелец схемы может отключить триггер аудита. Аудит инструмента писался после
вызова, сбой записи только логировался (AGENTS.md, правило 5).

Факты (проверено 2026-11-24):

- Код ядра (8788561): отмена во время вызова инструмента не оставляла `tool.call`; класс
  разговора повышался после вызова; `agent_runs.state` и аргументы в `pending` оставались после
  решения (на стенде у всех 20 решённых ожиданий); SQLAlchemy без `hide_parameters` включает
  параметры запроса (тексты сообщений) в текст ошибки; `error` хранил текст ответа шлюза.
- Регламент (EU) 2024/2690, приложение, п. 3.2.5: журналы хранятся и резервируются
  «predefined period» и защищаются от изменений; числа месяцев нет. Действует для облачных и
  managed-провайдеров (ст. 1). Traficom: 6-24 месяца, среда журналов отдельно от остальной.
  CNIL: 6-12 месяцев (по выдержке поиска).
- AI Act, ст. 19 и 26(6): журналы не менее 6 месяцев, только high-risk; Annex III с 2 декабря
  2027 (по artificialintelligenceact.eu).
- GDPR, ст. 5(1)(e): не дольше нужного; ст. 17(3)(b) и (e): исключения из удаления; ст. 20: только
  согласие или договор, не законный интерес.
- PostgreSQL 18.7 (опыт в одноразовом контейнере): владелец таблицы отключает триггер и удаляет
  строки; таблицу в схеме другой роли владелец БД не может ни изменить, ни удалить; `DROP TABLE`
  секции проходит несмотря на триггер TRUNCATE. `sha256()` встроен. Защиты от суперпользователя
  внутри БД нет.
- OpenBao 2.7.2 Transit: ed25519, по умолчанию `exportable=false` и `deletion_allowed=false`,
  отдельные пути sign и verify.
- LiteLLM 1.108.8: `maximum_spend_logs_retention_period`, проверок лицензии в коде очистки нет;
  промптов в SpendLogs на стенде нет. Open WebUI 0.13.3: настройки срока хранения чатов не
  найдено. Keycloak 26.8.2: события входа 30 дней, admin-события без срока.
- OTel GenAI: содержимое по умолчанию не собирается, статус Development.

## Варианты

Запись аудита инструмента:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **`tool.call.started` до вызова, итог после, нет записи = нет вызова** | Действие без следа невозможно | Две записи на вызов; БД недоступна = инструменты не работают |
| То же, но только для не `read_only` | Меньше записей | Чтение чужих данных без следа; против правила 5 |
| Только итог | Просто | Сбой или отмена = действие без записи |

Защита аудита от администратора БД:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Своя схема и владелец, цепочка хэшей в триггере, подписанные контрольные точки вне БД** | Без новых сервисов; подмена видна | Вставки идут по очереди; события после последней точки не защищены от суперпользователя |
| Цепочка пачками в фоне | Нет очереди вставок | Последние события вне цепочки |
| Отдельная СУБД или WORM сразу | Сильнее | Новый stateful-сервис против ADR-0003 |

Очистка:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Фоновый сервис с отдельной ролью, права по столбцам** | Нет DELETE у сервиса, тексты не читает | Ещё один контейнер |
| pg_cron | Внутри БД | Расширение, работает суперпользователем |
| Секции по месяцам | Быстрое удаление | Нет секции = отказ аудита = отказ платформы |

## Решение

1. **Сроки** (манифест v4, раздел `retention`; границы проверяет манифест):

   | Данные | По умолчанию | Границы |
   | --- | --- | --- |
   | `messages` | 90 дней от создания сообщения | 30-180 |
   | `agent_runs.state`, аргументы в `pending` | до решения или истечения | нет |
   | `model_calls`, `agent_runs`, пустые `conversations` | 365 дней | 180-730 |
   | `audit_events` | 365 дней | 180-730 |
   | SpendLogs LiteLLM, события Keycloak | 365 дней | как аудит |
   | Чаты Open WebUI | 90 дней без активности, но не дольше 180 дней от создания | как `messages` |
   | Журналы и телеметрия | 30 дней (сервер, ADR-0013) | |
   | Бэкапы | 35 дней; после восстановления удаления повторяются | |

   История чата Open WebUI хранится одним JSON, поэтому чат удаляется целиком: срок от последней
   активности, верхняя граница 180 дней от создания.
   Минимум 180 дней для аудита вшит ещё и в функцию удаления в БД. Допущение 180 дней из
   ADR-0006, п. 6 этим заменено.
2. **`platform-worker`**: тот же образ, команда `worker`, роль БД `platform_worker`, без ключей
   шлюза и Keycloak. Раз в минуту: истёкшие ожидания подтверждения = `expired`; `model_calls` и
   `agent_runs` в `started` дольше часа = `error` с причиной `abandoned`; начатые вызовы
   инструментов без итога дольше часа = `tool.call.unknown` (выполнено ли действие, неизвестно).
   Каждое закрытие = событие аудита с `actor_client` `platform-worker`. Раз в сутки очистка по
   срокам. Права по столбцам: тексты `messages` и `agent_runs.state` роль не читает. `state` и
   `pending` обнуляются в той же транзакции, что и решение.
3. **Запись до действия.** Перед каждым вызовом инструмента пишется `tool.call.started`
   (`call_id`); класс разговора (ADR-0011) повышается тогда же, а не после вызова. Если запись не
   удалась, вызов не выполняется. Итог `tool.call` с тем же `call_id` пишется при любом исходе,
   включая отмену запроса. Вызов модели, прямой или шаг агента, не начинается без
   строки `model_calls` в БД; итог шага и `model.call` пишутся сразу после ответа модели, потерянный
   итог закрывает worker.
4. **Защита аудита.** Схема `audit` и отдельный владелец: ни `platform`, ни роли сервисов не
   могут изменить таблицу. Цепочка хэшей `sha256` в триггере под advisory lock; поэтому события
   аудита вставляются последними в транзакции (иначе возможна взаимная блокировка со строками
   разговоров). Удаление только функцией владельца: начало цепочки и не моложе 180 дней.
   Контрольные точки (номер, хэш, счётчик) подписывает OpenBao Transit (ed25519) и хранит вне БД;
   у `platform-api` доступа к ключу нет. На стенде скрипт из `up.sh` и `backup.sh`, на сервере
   таймер раз в час и WORM-хранилище. Владелец `platform_audit` без входа; таблицу переносит и меняет
   `postgres/audit.sql` суперпользователем, а не миграции `platform`. Время, номер и хэши события задаёт
   БД. Проверка (`scripts/audit_chain.py`, только stdlib) не использует функции проверяемой БД:
   пересчитывает хэши, сверяет точки и их подписи, замечает обрезание и удаление моложе 180 дней.
   Точки связаны хэшами между собой и входят в бэкап.
5. **PII.** В аудите нет имён, email, аргументов, результатов и текстов ошибок, только коды;
   идентификатор IdP (`subject`) только если нашего id ещё нет. В `model_calls.error` и
   `agent_runs.error` только коды. Журнал исключений: типы и места без текстов; `hide_parameters`
   в SQLAlchemy; `log_error_verbosity=terse` в PostgreSQL.
6. **Граница с observability.** Аудит полный, транзакционный, без сэмплирования и только он
   используется для решений о доступе и расследований. OTel и журналы могут теряться, содержимого,
   имён и email в них нет, сбор содержимого GenAI выключен. Связь по `request_id`. Выбор
   инструмента: ADR-0013.
7. **Права субъекта данных.** Команды `subject export` и `subject erase`, одноразовый запуск
   отдельной ролью, с записью в аудит. Удаляются тексты, имя, email, идентичности, связь разговоров с
   чатами клиента и чаты Open WebUI; пользователь отключается. Аккаунт Open WebUI определяется по
   `antec_uid`, а не по идентификаторам чатов (их утверждает клиент). Журнал удалений вне БД
   (`subject.sh reapply`) повторяет их после восстановления из бэкапа. Аудит остаётся с UUID до своего срока: это псевдонимизация, данные остаются
   персональными. Основания, DPIA, порядок и сроки ответа, копия у провайдеров: ADR-0015.
8. **Порядок:** PR A: этот ADR, пп. 2 (без очистки), 3, 5; PR B: манифест v4, очистка, Open WebUI,
   LiteLLM, Keycloak, п. 7; PR C: п. 4 и проверка цепочки в smoke и `restore-verify`.
   ADR-0015 не блокирует: он меняет значения, а не механизм.

## Последствия

- Плюс: действие инструмента не может остаться без записи; сбой виден как `abandoned` или `unknown`.
- Плюс: подмена аудита администратором БД обнаруживается до последней контрольной точки.
- Минус: БД недоступна = инструменты агентов не работают.
- Минус: неудавшийся вызов тоже повышает класс разговора (строже ADR-0011, п. 3).
- Минус: в БД нет текста ошибки шлюза, разбор по коду, `gateway_request_id` и журналу LiteLLM.
- Минус: остаточный риск: суперпользователь БД переписывает события после последней точки,
  владелец хоста может всё; владелец БД `platform` может удалить БД целиком (видно сразу).
- Минус: запрос дольше часа worker сочтёт потерянным; поздний итог запишется поверх, в аудите
  будут оба события.
- Минус: события шагов агента до PR B при сбое процесса терялись.
- Минус: события аудита до миграции 0005 могут содержать тексты ошибок MCP; они только на
  добавление и уйдут по сроку.

## План выхода (как заменить)

Аудит это таблица PostgreSQL в документированной схеме и выгрузка JSONL; подпись проверяется
стандартным ed25519 без OpenBao. Worker заменяется любым планировщиком с теми же командами.

## Допущения и открытые вопросы

- Допущение: любой запрос короче часа (таймаут шлюза 300 с).
- [ ] § 21 закона 759/2004 (технический контроль сотрудников) и рекомендация Traficom для NIS не
      прочитаны: проверить в ADR-0015.
- Проверено в PR B: `Chats.delete_chat_by_id` Open WebUI 0.13.3 (models/chats.py) и схема на стенде;
  обновление Open WebUI требует перепроверки `adapters/open_webui.py`.
- [ ] Аккаунт Open WebUI (имя, email, папки, теги) `subject erase` не удаляет: это делает администратор
  Open WebUI; объединить после SCIM.
- Удаление снимает и блокировку пользователя в Platform API (новый вход = новый пользователь), поэтому
  доступ сначала закрывается в IdP.
- [ ] Запрос, который выполняется во время `subject erase`, может записать ответ после удаления:
  команду повторить.
- [ ] Обрезание конца файла точек вместе с аудитом на стенде не заметить: нужен WORM.
- [ ] Восстановление бэкапа старше файла точек даёт «обрезано»: файл точек берётся из бэкапа, новая
      точка ставится после разбора.
- [ ] WORM-хранилище контрольных точек на сервере.

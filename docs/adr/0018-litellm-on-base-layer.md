# ADR-0018: LiteLLM на стенде: версия, секреты без Vault, сеть, бюджеты (уточнение ADR-0001)

- Статус: предложено
- Дата: 2026-11-21
- Ответственный: CTO
- Связанные: ADR-0001, ADR-0002, ADR-0004, ADR-0007, ADR-0017,
  [policy/allowed-versions.yaml](../../policy/allowed-versions.yaml), [deploy/compose](../../deploy/compose/README.md)

## Контекст

ADR-0001 выбрал LiteLLM OSS и назначил PoC: версия и подпись образа, бюджет на конечного
пользователя по `user`, отчёт расходов, хранение секретов в OpenBao. Факты на 2026-11-21:

- Допущение ADR-0001 «1.108.7 последний патч LTS» неверно: вышли 1.108.8-1.108.14. Вне
  7-дневного карантина 1.108.8 (2026-11-13). OSV по 1.108.x пусто, открытых GHSA на линии нет
  (последний, GHSA-2rwg, закрыт в 1.108.6). 1.108.13 закрывает чтение чужих ключей без
  пользователя через `/key/info` (без GHSA).
- 1.108.0-1.108.9 подписаны ключом `cosign.pub` из коммита ротации `e82a3c6` (2026-10-23, после
  инцидента 2026-10-21); 1.108.10+ и 1.110+ подписаны keyless. Подпись 1.108.8 проверена для
  `litellm`, `litellm-database`, `litellm-non_root`.
- `litellm-non_root` работает под uid 65534, Prisma в офлайн-режиме, миграции БД при старте.
- Интеграция LiteLLM с HashiCorp Vault (и совместимым OpenBao) платная (`premium_user`).
  В OSS секреты задаются только ссылками `os.environ/` на переменные окружения.
- Бюджеты конечных пользователей (`/customer/*`) в OSS без проверок premium.
- Platform API ещё нет; Open WebUI по ADR-0002 должен ходить только в Platform API.

## Варианты

Доставка секретов в LiteLLM:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Файлы из OpenBao (secrets-render) + обёртка entrypoint, переносящая их в окружение процесса** | Без платных функций; секретов нет в `docker inspect`, argv, образе и репозитории; тот же поток, что у PostgreSQL и Keycloak | Значения видны в `/proc/1/environ` внутри контейнера (тот же uid); новый ключ применяется перезапуском |
| Интеграция LiteLLM с Vault/OpenBao | Ротация без перезапуска | Платная (Enterprise), противоречит ADR-0001 |
| `environment` в compose | Просто | Секреты в `docker inspect` и конфигурации; нарушает правило 5 AGENTS.md |

## Решение

1. **Версия:** LiteLLM 1.108.8, образ `ghcr.io/berriai/litellm-non_root` по digest; подпись
   проверена ключом из коммита ротации, digest сверен с denylist. Переход на 1.110.x после
   карантина (keyless-подпись).
2. **Секреты:** `antec/litellm` (мастер-ключ `sk-…`, salt key, копия пароля роли БД) и
   `antec/llm-providers` (ключи провайдеров, `scripts/set-llm-key.sh`, ввод без эха через stdin)
   в OpenBao. `secrets-render litellm` (токен `render-litellm`, только эти два пути) пишет файлы
   0400 с именами переменных; `litellm/entrypoint.sh` переносит их в окружение процесса и
   запускает штатный entrypoint. Salt key не меняется после первого запуска: им зашифрованы
   учётные данные в БД LiteLLM.
3. **Конфигурация в git:** `deploy/compose/litellm/config.yaml`; логические модели
   `chat-default` (Claude Opus 5.5) и `chat-fast` (Claude Haiku 5.5); `STORE_MODEL_IN_DB`
   выключен; карта цен из образа (`LITELLM_LOCAL_MODEL_COST_MAP`).
4. **Харденинг:** админка выключена (`DISABLE_ADMIN_UI`), вход по env-учётке выключен
   (`disable_env_credential_login`), мастер-ключ не возвращается API, документация API
   выключена, тексты запросов и ответов в БД не пишутся (`turn_off_message_logging`); ФС только
   для чтения, `cap_drop: ALL`, лимит памяти 1,5 GB.
5. **Сеть:** `data` (PostgreSQL), `llm` (internal, клиенты шлюза), `llm-egress` (выход к API
   провайдеров). Порт на хост не публикуется; проверка идёт изнутри контейнера.
6. **Бюджеты и учёт:** виртуальные ключи с бюджетом и списком моделей; конечный пользователь из
   поля `user` (или заголовка `X-OpenWebUI-User-Id`) с бюджетом через `/customer/*`. Источник
   истины расходов остаётся Platform API (ADR-0001, п. 4); колбэк в Platform API при его появлении.
7. **Open WebUI на стенде до появления Platform API** подключается к LiteLLM напрямую своим
   виртуальным ключом и передаёт пользователя заголовком. Это временное отклонение от ADR-0002,
   п. 1, только на локальном стенде; снимается, когда появится фасад Platform API.

## Последствия

- Плюс: проверено на стенде (`scripts/litellm-smoke.sh`): модели отвечают, запрещённая модель
  отклоняется, бюджет конечного пользователя срабатывает (422 `budget_exceeded`), расходы
  ключа и пользователя учитываются (Opus 5.5: 19/31 токенов = 0,000696 USD, совпадает с ценой
  провайдера), отозванный ключ не принимается; бэкап и восстановление БД `litellm` и секретов.
- Плюс: ни одной платной функции LiteLLM.
- Минус: секреты в окружении процесса LiteLLM; кто получит выполнение кода в контейнере, получит
  и ключи провайдеров. Это свойство любого шлюза, который сам ходит к провайдерам; снижается
  лимитами расходов у провайдера и ротацией (ADR-0004, п. 10).
- Минус: выход в интернет не ограничен доменами провайдеров (Docker Desktop без egress-прокси).
- Минус: LiteLLM пишет в лог префикс хэша отклонённого ключа; ключи хранятся хэшированными.

## План выхода (как заменить)

Без изменений относительно ADR-0001: клиенты знают только OpenAI-совместимый API и логические
имена моделей; секреты лежат в OpenBao и выгружаются файлами, поэтому другой шлюз получает их тем
же `secrets-render`.

## Допущения и открытые вопросы

- Допущение подтверждено: бюджет на конечного пользователя по `user` работает в OSS.
- [ ] Ограничение исходящего трафика LiteLLM доменами провайдеров (egress-прокси на сервере).
- [ ] Колбэк расходов в Platform API (ADR-0001, п. 4).
- [ ] Переход на 1.110.x после карантина (keyless-подпись, проверка identity).
- [ ] Ротация мастер-ключа и ключей провайдеров без простоя.

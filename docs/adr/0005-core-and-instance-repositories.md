# ADR-0005: Кодовая база: версионируемое ядро и отдельный репозиторий на каждую инсталляцию

- Статус: предложено
- Дата: 2026-11-21
- Ответственный: CTO
- Связанные: ADR-0004, [security/licensing.md](../security/licensing.md), [context/requirements.md](../context/requirements.md)

## Контекст

Сначала платформа работает только для Mtech. Затем Mtech хостит у себя отдельную инсталляцию
для каждого клиента со своей конфигурацией и своим набором компонентов (например, у клиента
канал Teams вместо Open WebUI). Требование: развитие у одного клиента не должно зависеть от
цикла разработки ядра или других клиентов.

При этом действуют NIS2 (управление уязвимостями) и ADR-0004: каждая уязвимость или
скомпрометированная зависимость должна быть закрыта во всех инсталляциях быстро.

## Варианты

| Вариант | Плюсы | Минусы | Стоимость поддержки |
| --- | --- | --- | --- |
| A. Форк всей кодовой базы на клиента | Полная независимость | Каждый security-патч делается N раз; форки расходятся, через год перенос исправлений почти невозможен; общие улучшения не доходят до клиентов | Растёт линейно с числом клиентов, быстро становится неподъёмной |
| B. Один репозиторий, общий релизный цикл для всех | Просто | Клиент зависит от общего цикла: ровно то, чего хотим избежать | Низкая |
| **C. Ядро как продукт + репозиторий инсталляции на клиента** | Клиент сам выбирает, когда обновлять ядро; клиентский код изолирован; патчи безопасности выпускаются один раз | Нужна дисциплина версий и поддержка нескольких версий ядра | Средняя, почти не растёт с числом клиентов |

## Решение (предложено)

Вариант C.

1. **Репозиторий ядра** (`antec.ai`): Platform API, контракты плагинов, базовые плагины,
   шаблон инсталляции, реестр версий. Выпускает релизы по semver: подписанные образы, SBOM,
   changelog.
2. **Репозиторий инсталляции** на каждую организацию (`instance-mtech`, `instance-<клиент>`),
   генерируется из шаблона. Содержит:
   - закреплённую версию ядра (по digest образов);
   - профиль: какие компоненты включены (Open WebUI или Teams-адаптер, набор моделей, MCP-серверы),
     политики, лимиты, классы данных;
   - клиентские плагины (агенты, MCP-серверы, адаптеры каналов), которые нужны только этому клиенту;
   - свой docker-compose и свои ADR, если клиент отклоняется от стандарта.
3. **Клиентский код только в плагинах.** Изменения ядра под одного клиента запрещены; если
   плагину не хватает точки расширения, она добавляется в ядро для всех.
4. **Поддерживаемые версии ядра:** текущая и предыдущая минорная (N и N-1). Security-патчи
   выпускаются для обеих; инсталляция на неподдерживаемой версии обязана обновиться.
5. **Изоляция:** у каждой инсталляции своя БД, свои секреты, свои ключи провайдеров, своя сеть.
   Допущение: на старте отдельная VM на клиента.

## Последствия

- Плюс: клиент не ждёт релизов ядра и не получает чужие изменения.
- Плюс: инцидент вроде компрометации LiteLLM закрывается одним патчем ядра и обновлением
  закреплённой версии в каждом репозитории инсталляции (это можно автоматизировать PR-ботом).
- Минус: нужны релизный процесс ядра и матрица совместимости плагинов с версиями ядра.
- Сделать: контракт плагинов (ADR-0008) должен быть стабилен до первого клиента.

## План выхода

Если модель не подойдёт, репозиторий инсталляции можно превратить в полноценный форк (вариант A):
он уже содержит всё, что нужно для самостоятельной сборки.

## Допущения и открытые вопросы

- Допущение: канал Teams реализуется как адаптер-плагин в репозитории инсталляции клиента;
  он потребует регистрации бота в экосистеме Microsoft. Детали проверить при проектировании адаптера.
- [ ] Хостинг инсталляций клиентов: отдельная VM на клиента или общий хост с изоляцией контейнеров.

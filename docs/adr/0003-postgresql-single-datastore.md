# ADR-0003: PostgreSQL как единственное хранилище прикладных данных

- Статус: принято
- Дата: 2026-11-21
- Ответственный: CTO
- Связанные: ADR-0001, ADR-0002

## Контекст

Команда небольшая, DevOps начинающие. Каждая дополнительная СУБД добавляет бэкапы, патчи,
мониторинг и компетенции. CTO предпочитает PostgreSQL для всего.

## Варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Только PostgreSQL (+ pgvector)** | Одна технология, один процесс бэкапа, SQL как стандарт | Нагрузка концентрируется в одном кластере |
| PostgreSQL + MongoDB + Redis (по требованию компонентов) | Компоненты работают «как задумано» | Три СУБД, SSPL у MongoDB |

## Решение

PostgreSQL 18 (версия по реестру) с pgvector для всех прикладных данных v1:
Keycloak, LiteLLM, Open WebUI, Platform API (история, аудит, расходы, реестр плагинов), DBOS,
векторы RAG. Каждый сервис получает отдельную БД, отдельную роль и лимит соединений.

Компоненты, которым нужна другая СУБД, в v1 не берутся (MongoDB, ClickHouse для Langfuse).
Redis в v1 не используется: одна реплика LiteLLM и Open WebUI работает без него.

Исключение: хранилище метрик и логов (VictoriaMetrics, VictoriaLogs). Это телеметрия, а не
прикладные данные; её потеря не ломает платформу.

## Последствия

- Плюс: один runbook бэкапа и восстановления, одна точка мониторинга.
- Минус: PostgreSQL становится критичным узлом. Нужны физические бэкапы с WAL-архивом вне хоста,
  ежемесячная проверка восстановления, в продакшне реплика с автоматическим failover.
- Минус: при горизонтальном масштабировании LiteLLM или Open WebUI понадобится Redis. Это решение
  принимается отдельным ADR при выходе за одну реплику.

## План выхода

Стандартный SQL и стандартный протокол PostgreSQL. Переезд на managed PostgreSQL без изменения кода.

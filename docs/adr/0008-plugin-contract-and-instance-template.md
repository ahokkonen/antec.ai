# ADR-0008: Контракт плагинов и механизм шаблона инсталляции

- Статус: предложено
- Дата: 2026-11-22
- Ответственный: CTO
- Связанные: ADR-0001, ADR-0004, ADR-0005, ADR-0006, ADR-0007, ADR-0009, ADR-0010 (в очереди),
  [ADR-0014](0014-release-process.md), ADR-0016, ADR-0017, ADR-0018

## Контекст

Инсталляции организаций живут в репозиториях `instance-<org>`, закрепляют версию ядра, клиентский
код только в плагинах (ADR-0005). Контракт должен быть стабилен до первого клиента. Открытые
вопросы других ADR: как инсталляция дополняет или переопределяет политики Cerbos ядра (ADR-0009,
п. 7), как подключаются её модели, MCP-инструменты и настройки. Сейчас логические модели заданы
трижды (`litellm/config.yaml`, `PLATFORM_MODELS`, `litellm_provision.py`), а compose стенда лежит в
ядре, потому что шаблона нет (ADR-0017).

Факты (проверено 2026-11-22):

- Cerbos 0.57.0: scope ресурса в AuthZEN передаётся плоским свойством
  `resource.properties["cerbos.scope"]` (`internal/svc/authzen_svc.go`, `toResource`). Scope
  `a.b` ищется от самого узкого к базовому (без scope); цепочка без пропусков. Режимы
  `scopePermissions`: `SCOPE_PERMISSIONS_OVERRIDE_PARENT` (по умолчанию: первое сработавшее
  правило снизу вверх решает) и `SCOPE_PERMISSIONS_REQUIRE_PARENTAL_CONSENT_FOR_ALLOWS` (дочерний
  scope только сужает). Без `lenientScopeSearch` для запрошенного scope обязана существовать
  политика каждого вида ресурса; с ним Cerbos откатывается к ближайшему существующему scope.
  Драйвер `disk` читает всё дерево каталога.
- LiteLLM 1.108.8: `include:` в конфигурации (`proxy/common_utils/config_includes.py`) склеивает
  списки, а любой другой ключ включённого файла целиком заменяет ключ основного. Несколько
  записей `model_list` с одним `model_name` = балансировка, а не замена.
- MCP: актуальная ревизия спецификации 2026-07-28 (без сессий и handshake, Streamable HTTP),
  предыдущая 2025-11-25. Подсказки инструментов (`readOnlyHint`, `destructiveHint`) сообщает сам
  сервер, доверять им нельзя.
- Copier 9.19.1 (MIT) умеет обновлять сгенерированные проекты из шаблона, но за 2026 год у него
  7 GHSA (path traversal, symlinks, задачи без запроса) и 13 прямых зависимостей.

## Варианты

Где исполняется код плагинов:

| Вариант | Плюсы | Минусы | Стоимость поддержки |
| --- | --- | --- | --- |
| **Только вне процесса Platform API: MCP, OpenAI-совместимый API, OIDC** | Плагин не получает ключ шлюза, БД и токены других пользователей; свой цикл релизов и язык; граница = стандартный протокол | Сеть и отдельный сервис на плагин | Низкая |
| Python entry points в Platform API | Быстро, без сети | Код клиента с правами ядра; связность версий Python и зависимостей; уязвимость плагина = уязвимость ядра | Растёт с числом клиентов |

Политики инсталляции:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Scope Cerbos = id инсталляции, `OVERRIDE_PARENT`, `lenientScopeSearch`** | Инсталляция и расширяет, и сужает; базовые политики ядра работают без изменений; политики ядра обновляются вместе с ядром | Инсталляция может ослабить политику ядра; неотменяемые правила нужно держать в коде |
| Scope с `REQUIRE_PARENTAL_CONSENT_FOR_ALLOWS` | Ядро = потолок прав | Новые роли и модели инсталляции требуют правки ядра под клиента (запрещено ADR-0005) |
| Свой каталог политик инсталляции вместо ядра | Полная свобода | Изменения политик ядра не доходят до инсталляций |

Шаблон и обновление:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Тонкая инсталляция: манифест + политики + плагины; всё общее приходит с версией ядра; `init` из `templates/instance`** | Обновление = смена версии ядра; без новых зависимостей; шаблон почти не меняется | Нужен инструмент рендера в ядре |
| Copier (`copier update`) | Трёхстороннее слияние шаблона | Новая зависимость с историей уязвимостей; шаблон с кодом задач |
| Шаблон репозитория GitHub | Ноль инструментов | Обновлений нет: копии расходятся (вариант A ADR-0005) |

Привязка к версии ядра до релизного процесса:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **git submodule `core/` на тег ядра** | Стандартный git; точный коммит; compose, политики и инструменты ядра на месте | Весь исходный код ядра в рабочей копии инсталляции |
| Подписанный бандл релиза | Только нужные файлы, проверка подписи | Нужен релизный процесс (ADR-0014) |

## Решение

1. **Плагины только вне процесса Platform API**, через стандартные протоколы:
   - инструменты: MCP-сервер (Streamable HTTP) с правами пользователя через token exchange
     (ADR-0007), секреты в OpenBao;
   - каналы (Teams, Telegram и др.): отдельный сервис, клиент OpenAI-совместимого фасада со своим
     OIDC-клиентом Keycloak (`azp` в `allowed_clients`);
   - модели, политики и настройки: декларативно в репозитории инсталляции;
   - агенты: раздел `agents` манифеста зарезервирован, формат (`AgentSpec`) и исполнение решает
     ADR-0010; до него раздел запрещён валидатором.
   Python entry points и импорт кода инсталляции в процесс Platform API не используются.
2. **Манифест `instance.yaml`, схема v1** (`tools/instance`, Pydantic, неизвестные поля = ошибка):
   - `schema_version: 1`;
   - `instance.id`: slug организации (`[a-z][a-z0-9-]{1,30}`), он же scope политик Cerbos;
     `instance.name`;
   - `core.version`: версия ядра, должна совпадать с `VERSION` закреплённого ядра;
   - `models`: логическое имя (как в ADR-0006), описание и параметры LiteLLM из белого списка
     (`model`, `api_key`, `api_base`, `api_version`, `rpm`, `tpm`, `timeout`); `api_key` только
     ссылкой `os.environ/<имя>` на переменную из набора, который выгружает ядро
     (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY`); имена моделей уникальны;
   - `mcp_servers`: `name`, `url`, `audience` (аудитория token exchange, ADR-0007),
     `protocol_version` (`2025-11-25` или `2026-07-28`), `tools` (белый список: имя и
     `read_only`; всё, что не помечено `read_only: true` в манифесте, требует подтверждения
     человеком, подсказкам сервера не доверяем), `secrets` (имена ключей в OpenBao
     `antec/plugins/<name>`). Раздел проверяется сейчас, исполняется вместе с MCP-клиентом;
   - `settings`: только параметры Platform API из белого списка (`allowed_clients`,
     `max_request_bytes`, `gateway_timeout_seconds`, `log_level`). Адреса сервисов, OIDC,
     секреты и сеть задаёт ядро.
3. **Рендер.** `tools/instance render` проверяет манифест и политики и пишет производные файлы:
   `litellm-models.yaml` (только ключ `model_list`) и `platform-api.env` (`PLATFORM_MODELS`,
   `PLATFORM_POLICY_SCOPE`, параметры из `settings`). Модели задаются в одном месте: из манифеста
   их берут LiteLLM (`include`), Platform API (env) и подготовка ключа `platform-api` в LiteLLM.
   Конфигурация LiteLLM ядра больше не содержит `model_list`.
4. **Политики.** Ядро: `policies/cerbos` без scope (базовые). Инсталляция: `policies/` в своём
   репозитории, каждая resource и principal policy со `scope` = `instance.id` и
   `scopePermissions: SCOPE_PERMISSIONS_OVERRIDE_PARENT` (валидатор отклоняет другое), тесты
   рядом. Cerbos читает `/policies/core` и `/policies/instance` одного дерева,
   `lenientScopeSearch: true`: виды ресурсов, которые инсталляция не переопределила, решают
   политики ядра. Platform API передаёт scope из `PLATFORM_POLICY_SCOPE` в каждом ресурсе.
   Правила, которые инсталляция не должна ослаблять (отказ disabled-пользователю, отказ субъекту
   без ролей, подтверждение необратимых действий), остаются в коде Platform API, а не в политиках.
   В CI `cerbos compile` проверяет политики ядра и инсталляции вместе.
5. **Шаблон.** `templates/instance/` в ядре и `tools/instance init <каталог> --id <id>`: манифест,
   каталог политик с примером и тестом, `compose.override.yaml` для сервисов плагинов, `plugins/`,
   `docs/adr/`, README. Обновление инсталляции = смена версии ядра и при необходимости правка
   манифеста по changelog ядра; повторной генерации из шаблона нет.
6. **Связь с ядром** до релизного процесса: git submodule `core/` на тег ядра. Стенд инсталляции
   запускается скриптами ядра: `core/deploy/compose/scripts/up.sh` с `ANTEC_INSTANCE_DIR` =
   корень инсталляции; `compose.override.yaml` инсталляции подключается к compose ядра. После
   ADR-0014: подписанный бандл и образы ядра по digest вместо submodule.
7. **Dev-инсталляция ядра** `instances/dev/`: стенд и CI ядра работают через тот же контракт
   (модели `chat-default`, `chat-fast` и пример модели и политики инсталляции).

## Последствия

- Плюс: открытые вопросы ADR-0009 (политики инсталляций) и ADR-0006 (модели) закрыты одним
  механизмом; модели больше не дублируются.
- Плюс: клиентский код не попадает в процесс ядра; плагин заменяем любым сервером того же протокола.
- Плюс: без новых зависимостей (Pydantic и PyYAML уже в реестре через pincheck).
- Минус: инсталляция может ослабить базовые политики ядра (`OVERRIDE_PARENT`); защищает ревью
  PR инсталляции и тесты её политик, неотменяемое держится в коде.
- Минус: `lenientScopeSearch` скрывает опечатку в scope; валидатор сверяет scope политик с
  `instance.id`, а Platform API берёт scope из того же манифеста.
- Минус: стенду нужен `uv` на хосте (рендер манифеста).
- Сделать: клиенты Keycloak для аудиторий MCP и каналов по манифесту; исполнение `mcp_servers`
  вместе с MCP-клиентом; раздел `agents` в ADR-0010; бандл ядра в ADR-0014.

## План выхода (как заменить)

Манифест и производные файлы документированы схемой; при отказе от инструмента файлы LiteLLM,
env и политики пишутся вручную. Смена PDP: scope Cerbos переносится в аналог (тенант OPA, модель
OpenFGA) в адаптере `authzen.py`. Отказ от тонкой инсталляции: репозиторий инсталляции с ядром
в submodule уже содержит всё для форка (план выхода ADR-0005).

## Допущения и открытые вопросы

- Допущение: одной инсталляции хватает одного уровня scope (без отделов и регионов); вложенные
  scope (`mtech.finance`) добавляются без изменения контракта.
- [ ] Реестр версий для образов плагинов инсталляции: свой `policy/allowed-versions.yaml` в
      репозитории инсталляции и проверка pincheck по двум файлам (сейчас `--policy` один).
- [x] Клиенты Keycloak для MCP-аудиторий из манифеста: `keycloak.py apply` создаёт их по
      `mcp_servers` (ADR-0010). Клиенты каналов: открыт.
- [ ] Совместимость манифеста с версиями ядра N и N-1 (ADR-0014).

# ADR-0011: Классы данных и маршрутизация моделей

- Статус: предложено
- Дата: 2026-11-22
- Ответственный: CTO
- Связанные: ADR-0001, ADR-0005, ADR-0006, ADR-0008, ADR-0009, ADR-0010, ADR-0012 (в очереди),
  ADR-0015 (в очереди), [context/requirements.md](../context/requirements.md),
  [architecture/roadmap.md](../architecture/roadmap.md)

## Контекст

Через платформу проходят данные разных классов (requirements.md). В v1 в облачные модели
разрешены любые данные; локальные модели только в v2, и тогда чувствительные данные должны
уходить на них «без изменения кода агентов» (roadmap.md). Классы данных входят в профиль
инсталляции (ADR-0005). Нужен механизм уже в v1: что можно отдавать какой модели, кто это
решает, как это видно в аудите.

Факты (проверено 2026-11-22):

- LiteLLM 1.108.8 (`litellm/router.py`): `fallbacks`, `default_fallbacks`,
  `context_window_fallbacks`, `content_policy_fallbacks` между логическими моделями;
  тег-маршрутизация (`enable_tag_filtering`, теги запроса выбирают развёртывания,
  `router_strategy/tag_based_routing.py`); несколько записей `model_list` с одним `model_name`
  = балансировка. На стенде ничего из этого не включено, `num_retries: 0`. Fallback между
  логическими моделями может отправить данные модели с меньшим допуском; теги запроса
  утверждает вызывающий.
- Cerbos 0.57.0, AuthZEN (`internal/svc/authzen_svc.go`): из `context` запроса берутся только
  `requestId` и auxData (JWT); атрибуты для политик передаются свойствами ресурса
  (`resource.properties`), как уже передаётся `cerbos.scope` (ADR-0008).
- Ввод пользователя Platform API сейчас не классифицирует (гардрейлы и детектор PII позже).

## Варианты

Где определяется класс:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Класс у источника (ввод, инструмент, позже документ), допуск у модели; всё в манифесте** | Детерминированно, известно до вызова; без отслеживания «заражения» | Ввод пользователя без классификатора получает класс по умолчанию |
| Классификатор содержимого (PII, ключевые слова) | Видит реальные данные | Вероятностный, ложные срабатывания; это гардрейлы (отдельный ADR) |
| Класс выбирает пользователь | Просто | Нет в OpenAI API и Open WebUI; ошибка пользователя = утечка |

Кто проверяет:

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **Код Platform API (инвариант) + атрибут `data_class` в Cerbos (только ужесточение)** | Инсталляция не может ослабить допуск; роли по классам в политиках | Два места: инвариант и политика |
| Только политика Cerbos | Одно место | Инсталляция с `OVERRIDE_PARENT` (ADR-0008) может ослабить допуск |
| LiteLLM (теги, маршрутизация) | Готовые механизмы | Теги утверждает вызывающий; шлюз заменяем (ADR-0001) |

## Решение

1. **Четыре упорядоченных класса ядра:** `public` < `internal` < `confidential` < `restricted`.
   Набор фиксирован. Персональные данные особых категорий (GDPR, ст. 9) = `restricted`.
2. **Манифест, схема v3** (v1 и v2 валидны, новые поля только в v3):
   - `data.default_class` (по умолчанию `internal`): класс всего, что вводит пользователь;
   - у модели `max_data_class` (по умолчанию `restricted`: в v1 облачным моделям разрешены
     любые данные): верхний допуск;
   - у инструмента MCP `data_class` (по умолчанию `data.default_class`): класс данных, которые
     инструмент возвращает модели (например, почта M365 `confidential`).
   Рендер пишет `platform-api/models.json` (допуски) и `data_class` в `mcp_servers.json`,
   `PLATFORM_DEFAULT_DATA_CLASS` в env.
3. **Инвариант в коде Platform API:**
   - модель с допуском ниже `default_class` не показывается в `/v1/models`, прямой вызов = 403
     `data_class_forbidden`;
   - агент, чья модель не допущена к `default_class`, скрыт и не вызывается;
   - инструмент агента с `data_class` выше допуска модели агента отклоняется до вызова:
     данные не попадают в модель, модель получает текст отказа, аудит `tool.call` deny с
     причиной `data_class`. Класс известен до вызова, поэтому отслеживать «заражение»
     разговора не нужно; подтверждать такой вызов не предлагается;
   - `tools/instance validate` предупреждает об агентах с недоступными по классу инструментами.
4. **Cerbos:** `data_class` передаётся свойством ресурса `model` (класс запроса) и `tool` (класс
   инструмента). Политики инсталляции могут ужесточить (например, `confidential` только для
   роли `finance`), ослабить инвариант п. 3 не могут.
5. **Маршрутизация:** логическая модель = граница допуска. Все развёртывания одного
   `model_name` в LiteLLM имеют один допуск (балансировка и замена провайдера внутри модели
   разрешены). Fallback между логическими моделями и тег-маршрутизация в манифест не
   выносятся: белый список `litellm_params` их не пропускает, рендер не пишет `router_settings`.
   Автоматическое перенаправление на модель с нужным допуском откладывается до v2 (локальные
   модели); в v1 отказ. В v2 агенту с чувствительными данными в манифесте задаётся локальная
   модель: код агента не меняется.
6. **Аудит:** `data_class` в `model.call`, `agent.run` и `tool.call`; отказы по классу с
   причиной `data_class`, отдельно от отказов политики (`policy`).

## Последствия

- Плюс: механизм работает с v1, хотя в v1 все модели допущены ко всему; переход к v2 = смена
  допусков и моделей в манифесте.
- Плюс: инсталляция не может обойти допуск политикой; ужесточение по ролям возможно.
- Минус: ввод пользователя всегда `default_class`; вставленные пользователем данные выше
  класса не распознаются до гардрейлов.
- Минус: coding-агенты ходят в LiteLLM напрямую, классы для них задаются только списком
  моделей ключа.
- Сделать: классификация ввода (гардрейлы, PII); класс документов RAG; `route_for_class` в v2.

## План выхода (как заменить)

Классы и допуски в манифесте, проверка в Platform API: замена шлюза или PDP не меняет их.
Отказ от своих классов: допуски всех моделей `restricted` и `default_class` любой, механизм
становится прозрачным.

## Допущения и открытые вопросы

- Допущение: одного уровня допуска на логическую модель достаточно (без допуска по региону и
  сроку хранения провайдера); сведения о провайдерах для DPIA ведутся в ADR-0015.
- [ ] Классификация ввода пользователя и ответов инструментов по содержимому (гардрейлы).
- [ ] Класс документов RAG и допуск на поиск.
- [ ] Автоматическое перенаправление по классу (`route_for_class`) с локальными моделями (v2).
- [ ] Классы для coding-агентов с личными ключами LiteLLM.

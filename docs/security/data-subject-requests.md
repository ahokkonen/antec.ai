# Запросы субъекта данных: runbook

Обновлено: 2026-11-26. Основание: GDPR, ст. 12, 15, 17, 20; ADR-0012, п. 7; ADR-0015.
В инсталляции клиента запрос получает клиент (контролёр); Mtech помогает как обработчик (ст. 28(3)(e)).

## Сроки

- Ответ без промедления и не позже месяца с получения запроса (ст. 12(3)).
- Продление ещё на два месяца при сложности: сообщить субъекту в первый месяц с причинами.
- Отказ (ст. 17(3)): сообщить в течение месяца с причиной и правом жалобы надзорному органу.

## Шаги

1. Зарегистрировать запрос (дата, канал, тип) в журнале запросов инсталляции.
2. Проверить личность: вход через IdP организации или подтверждение через HR. Не по одному email.
3. Найти пользователя: `deploy/compose/scripts/subject.sh find` (email со stdin).
4. Выгрузка (ст. 15, 20): `subject.sh export <id> > файл.json`. Файл передать защищённым каналом,
   затем удалить. В выгрузке нет данных других людей, кроме собственных разговоров субъекта.
5. Удаление (ст. 17), по порядку:
   1. закрыть доступ в IdP (Entra ID, Keycloak): иначе новый вход создаст нового пользователя;
   2. `subject.sh erase <id>` (тексты, имя, email, идентичности, чаты Open WebUI);
   3. аккаунт Open WebUI (имя, email, папки) удаляет администратор Open WebUI;
   4. пользователя в Keycloak удаляет администратор realm;
   5. в LiteLLM остаётся только UUID пользователя в учёте расходов, это псевдоним.
6. Ответ субъекту: что выгружено или удалено; что остаётся и почему (аудит и метаданные до срока
   ADR-0012, основание ст. 17(3)(b), (e)); бэкапы удаляются в течение 35 дней.
7. После восстановления из бэкапа: `subject.sh reapply`.

## Что не входит

- Решения о субъекте платформа не принимает (ADR-0015, п. 2): ст. 22 не применяется.
- Данные у провайдеров моделей: по их срокам (ADR-0015, факты); запрос провайдеру, только если
  у них включено хранение.
